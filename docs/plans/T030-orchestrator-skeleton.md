# Plan: T030 DeepAgents orchestrator skeleton with CompositeBackend and TodoList middleware

Backlog T030 (epic EP3). Branch `feat/orchestrator-skeleton` off `dev`. Gate 1 approved 2026-10-25 (batch approval). Depends on T005 (merged). ADR-0001.

## Goal
`rootcause_agents` builds the orchestrator with `create_deep_agent`: problem-framing system prompt, todo planning, a CompositeBackend that persists `/memories/` and `/skills/` in a LangGraph store and keeps everything else per thread, a checkpointer, and `interrupt_on` for expensive `run_sql` calls. No real subagents yet (T032 onward); no LLM calls in tests.

## Design
- Model ids: new `Settings` fields (per-role resolution later moved to `rootcause_core.clients` in T008) `orchestrator_model` (default `anthropic:claude-opus-5`), `fast_model` (default `anthropic:claude-sonnet-5`), `reasoning_model` (default `anthropic:claude-opus-5`), `scan_row_threshold` (default 5_000_000) added to `rootcause_core.settings`. Model objects are created with `langchain.chat_models.init_chat_model` only when no model is injected.
- `rootcause_agents/backends.py`: `build_backend(store: BaseStore | None) -> CompositeBackend` routing `/memories/` and `/skills/` to `StoreBackend(store)` and the default to `StateBackend()`; `build_checkpointer(settings)` returning `InMemorySaver` when `settings.environment != prod` and no database is reachable, otherwise a Postgres saver from `database_url` (factory only; connection opened by the API lifespan in T035). Tests use in-memory saver and `InMemoryStore`.
- `rootcause_agents/tools/sql.py`: `QueryExecutor` Protocol (`explain(sql) -> QueryEstimate(estimated_rows, estimated_cost)`, `run(sql, purpose) -> QueryResult`) and `make_sql_tools(executor, threshold) -> list[BaseTool]` producing `run_sql` and `explain_sql` tools over the injected executor (real executor lands in T012). `run_sql` first calls `explain`; if `estimated_rows > threshold` it returns a structured "approval required" payload that the harness turns into an interrupt via `interrupt_on={"run_sql": True}` configured in the orchestrator.
- `rootcause_agents/prompts/orchestrator.md`: system prompt with the 5 Whys problem template (what, when, where, impact), the rule to reject vague statements and ask the user to quantify, planning with `write_todos`, and the evidence rule (nothing in a report without an executed query).
- `rootcause_agents/orchestrator.py`: `build_orchestrator(*, model=None, settings=None, store=None, checkpointer=None, executor=None, extra_tools=()) -> CompiledGraph` calling `create_deep_agent(model=..., tools=[...sql tools, *extra_tools], system_prompt=..., middleware=[TodoListMiddleware()], backend=build_backend(store), checkpointer=..., interrupt_on={"run_sql": True})`. Exposes `OrchestratorHandle` frozen dataclass with `graph`, `store`, `checkpointer` for the API.
- `rootcause_agents/graph.py`: module-level `graph = build_orchestrator()` is NOT created at import; instead `apps/api/langgraph.json` keeps the placeholder until T035 wires the orchestrator with a lifespan-managed store (note in README).
- Dependencies (packages/agents): `deepagents>=0.4`, `langchain>=1.0`, `langgraph>=0.4`, `langgraph-checkpoint-postgres>=2.0`, `langchain-anthropic>=0.3`, workspace `rootcause-core`. Confirm exact current names and APIs against the LangChain docs (the langchain-docs MCP server is available) and pin what resolves.

## Tests (tester-owned, RED first; no network, no real LLM)
Settings fields and defaults; `build_backend` routes `/memories/x.md` writes to the store and `/scratch/x.md` to state (use the backend's own API or run the agent's `write_file` tool with a fake model); `make_sql_tools` with a fake executor: `explain_sql` returns the estimate, `run_sql` below threshold executes and returns rows, above threshold returns the approval payload and does not execute; `build_orchestrator` with a fake chat model (`GenericFakeChatModel` or a scripted `FakeMessagesListChatModel` emitting a `write_todos` tool call, then a `run_sql` call below threshold, then a final answer) runs end to end on `InMemorySaver` and the thread state contains todos and the tool result; a second invoke on the same `thread_id` resumes with prior messages (checkpointer works); invoking with a scripted `run_sql` above threshold produces an interrupt (`graph.get_state(config).next` non-empty or `__interrupt__` in the result) and resuming with approval continues; the system prompt file loads and contains the four template fields; coverage >= 80%.

## Acceptance (backlog)
A thread survives an API restart and resumes from the checkpointer (in-memory saver in tests, Postgres factory covered by a unit test of the factory selection); interrupt fires when the estimate exceeds the threshold and resumes on approval.
